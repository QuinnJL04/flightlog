## Environment gotchas

- **Node version matters.** System default was v20.12.2, too old for stable
  Prisma (needs 20.19+). Upgraded to Node 24.20.0 via nvm and set as default
  (`nvm alias default 24.20.0`), but **new shells don't auto-switch** —
  `.bashrc` sources `nvm.sh` but never calls `nvm use`. Every command in a
  fresh shell needs `source ~/.nvm/nvm.sh && nvm use 24.20.0` first, or you'll
  silently be back on v20.12.2 (`node -v` to check).
- `prisma` CLI's `latest` dist-tag currently points to an 8.0.0-rc.x
  prerelease. We pinned `prisma` and `@prisma/client` both to `7.10.0` — check
  before running any blind `npm install prisma@latest`.
- Prisma 7 requires an explicit driver adapter (no more implicit connection).
  We use `@prisma/adapter-pg`. See `src/lib/prisma.ts` for the shared client
  (globalThis-cached singleton pattern for dev hot-reload).
- The generated Prisma client (`src/generated/prisma`) is gitignored — it's
  regenerated by a `postinstall: prisma generate` script in `package.json`.
  This was a real bug once already: Vercel's build failed with "Cannot find
  module" until the postinstall hook was added. Don't remove it.
- **Clerk Core 3 broke a lot of what LLMs "know".** We're on `@clerk/nextjs`
  7.8.4. `<SignedIn>`, `<SignedOut>`, and `<Protect>` were **removed** — they
  still export, but their type is `never`, so using one is a compile error.
  Replacements: `<Show when="signed-in">`, `<Show when="signed-out">`,
  `<Show when={{ role: "admin" }}>`, all with an optional `fallback` prop.
  Also: `auth()` and `clerkClient()` are now async, and `auth.protect()` is
  called directly rather than off `auth()`'s return value. The Vercel `auth`
  skill is *also* stale on this. **Check
  `node_modules/@clerk/nextjs/dist/types/` before writing Clerk code** — the
  removal shims carry precise migration instructions in their JSDoc.
- `prisma migrate dev` is interactive and fails in a non-TTY agent shell
  ("environment is non-interactive"). Workaround that works:
  `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script`
  into a hand-made `prisma/migrations/<timestamp>_<name>/migration.sql`, then
  `prisma migrate deploy`. Note Prisma 7 renamed the diff flags
  (`--from-schema-datasource` → `--from-config-datasource`).
- **`sslmode` is pinned in code, not in the env.** Neon's `DATABASE_URL`
  ships `?sslmode=require`. `pg` currently treats that as `verify-full`, but
  pg v9 / pg-connection-string v3 will switch it to libpq semantics (encrypt,
  don't verify the cert) — a silent security downgrade via dependency bump,
  and it emits a runtime warning today. `src/lib/prisma.ts` rewrites
  `sslmode=require` → `sslmode=verify-full` in `resolveConnectionString()`.
  Deliberately done in code, not `.env.local`, because that file is
  regenerated by `vercel env pull` and wouldn't cover production. Verified
  Neon accepts `verify-full`. Don't "simplify" it back out.
- Prisma config (`prisma7.config.ts`) loads env vars from `.env.local`
  explicitly (not `.env`, which doesn't exist in this project — deleted the
  placeholder Prisma created). Any one-off Node/tsx script that needs
  `DATABASE_URL` (like the seed script) must be run through `dotenv-cli`:
  `dotenv -e .env.local -- tsx <script>`. Only Next.js auto-loads `.env.local`.

## Next up: tasks 5-8 (scoped 2026-09-01)

Owner asked to write ALL of tasks 5-8 themselves with guidance, so the usual
"agent does the plumbing" split does not apply here. Scaffold with TODOs only.

Owner asked for three things after using the dashboard: make it faster, make
the "log flight" button visibly react to a click, and stop invalid submissions
from throwing a full-page error that needs a reload. Tasks 6 and 7 are the same
refactor from two ends, so 7 depends on 6.

**Measured baseline** (dev, Neon `us-east-1`): connect 249ms, per-query round
trip 26ms, `POST /dashboard` 927ms cold / 218ms warm. Logging one flight fires
~6 sequential queries: user lookup, trip lookup, airline upsert, flight insert,
then `revalidatePath` re-renders and does user lookup + `findMany` again.
Nothing is algorithmically wrong — the cost is round-trip count, not code.

### Task 5 — Fewer round trips  *(OWNER writes)*
- Wrap `getCurrentUser` in React `cache()`. The Server Action and the
  re-render it triggers happen in **one request**, so `cache()` collapses the
  duplicate user lookup. Removes 1 of 6 queries.
- Fold the trip lookup into the user query with `include: { trips: ... }`.
  Removes another. Target: 6 queries -> 4, ~50ms.
- Do NOT chase this further. The remaining cost is network latency to
  Virginia; the real perceived win is Task 8.

### Task 6 — Action returns errors instead of throwing  *(OWNER writes)*
- `addFlight` currently `throw`s on bad input, which Next surfaces as the dev
  error overlay and requires a reload. Change it to **return** a serializable
  state object (`{ error?: string }`) and change the signature to
  `(prevState, formData) => Promise<State>`, which is what `useActionState`
  requires.
- Keep the `requireCurrentUser()` check throwing — an unauthenticated caller
  is not a validation error, and that endpoint is publicly POSTable.

### Task 7 — Client form with `useActionState`  *(OWNER writes)*
Covers both the pending button and the inline errors. This is the owner's
first `"use client"` component and first React hook — do not write it for them.
- `const [state, formAction, isPending] = useActionState(addFlight, {})`
- `isPending` -> disable the button and swap its label ("LOGGING...").
- `state.error` -> render inline above the form. No reload, no error screen.
- Teaching point: the action's return value must be **serializable**, because
  it crosses the network back from the server.

### Task 8 — Optimistic insert  *(OWNER writes, optional)*
- `useOptimistic` to append the flight to the list on the current frame, before
  the server responds. This is what actually makes it *feel* instant — Task 5
  shaves ~50ms, this removes the entire wait from perception.
- See `node_modules/next/dist/docs/01-app/02-guides/interactive-apps.md`,
  Step 4, for the exact server-list + pending-list pattern.

## Working style notes

- Owner wants to learn TypeScript hands-on, but **learns by breaking things,
  not by reading prose.** They explicitly called long code walkthroughs "too
  verbose" (2026-09-01) and said concepts are "quite simple to understand by
  breaking it on my end and then seeing how it works." Give terse
  **change this → this breaks → because** tables instead of essays, and
  distinguish compile-time from runtime breakage. Open-ended quiz questions
  stall out; "change this line, tell me what happened" works. Explain at
  length only when they ask a direct question.
- Scaffold-and-TODO is the agreed division of labor: the agent writes plumbing
  (auth wiring, API clients, migrations, datasets), the owner writes the app
  code from `// TODO(you):` stubs. Don't fill their TODOs unless asked.
- Confirm scope before each new phase/feature — phases were originally
  sketched in one line each and needed fleshing out via clarifying questions
  before building (hosting choice, users-table scope, UI scope, etc.). Don't
  assume — ask.
- Deployment/provisioning steps that need browser-based auth or ToS
  acceptance (Vercel GitHub App install, Neon marketplace terms) can't be
  done from the CLI non-interactively — pause and hand the owner a direct
  link rather than guessing.
